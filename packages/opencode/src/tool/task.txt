Launch a new subagent (worker thread) to handle complex, multistep tasks autonomously.

You are the orchestrator. Every subagent runs in its own session with its own context window, its own tool allowlist, its own role, and its own system prompt. You define the subagent fully at call time — there are no pre-registered agent types to choose from. Use this tool to delegate real work (anything that touches the environment or needs sustained focus) to a subagent, and keep the orchestrator context lean for planning, routing, and synthesis.

When to spawn a subagent:
1. Any real work in the environment — reading files, running commands, searching code, writing. Delegate; do not do it in the orchestrator.
2. Parallelizable workstreams — independent subtasks. Launch multiple Task calls in a single message (one tool_use each) to run concurrently.
3. Distinct context domains — a "research" workstream and an "implementation" workstream should not pollute each other's context. Each gets its own subagent. Pass relevant findings between them through your prompts deliberately.
4. Long or deep workstreams — tasks that require sustained focus (e.g. understand a module → plan fixes → implement) benefit from a persistent subagent. Reuse it via task_id.

When NOT to spawn a subagent:
- A specific file path is already known — use Read or Glob directly.
- Searching for a specific class/function — use Glob or Grep directly.
- Searching within 2-3 known files — use Read directly.
- Pure reasoning you can do from context already loaded — just answer.
- The task is trivial (typo fix, single-line rename) — do it inline.

Defining the subagent (parameters):

  - description (required): 3-5 word label for the task. Shown in UI.

  - prompt (required): the actual task the subagent should perform. Must be self-contained — the subagent starts with empty context. Include the goal, what's already known (so the subagent does not re-derive it), what to produce, and how to verify. State explicitly whether you expect code changes or research-only.

  - role (required): a short role label that names what the subagent IS for this call (e.g. "security reviewer", "api doc writer", "migration planner", "test coverage scout"). Used in the session title and injected into the subagent's system context as "You are operating in the role of: <role>." so it behaves in-character.

  - allowed_tools (strongly recommended): an array of tool IDs the subagent is allowed to call. When set, every other tool (write, edit, bash, todowrite, mcp tools, custom tools) is denied and hidden from the subagent's tool catalog. You may include any tool you yourself own — including "task" itself, which lets the subagent spawn its own sub-subagents with a further-narrowed tool set. Scope the subagent to the minimum tools it needs — a research subagent usually only needs ["read","grep","glob","webfetch"]; a focused edit subagent might get ["read","edit","bash"]; a reviewer might get only ["read","grep"]; a mid-tier orchestrator might get ["read","grep","task"]. Omit only when you deliberately want the baseline worker's full default tool set (rare).

    Ownership rule: allowed_tools MUST be a subset of the tools you yourself own. You cannot grant a subagent a tool you do not have — e.g. a subagent scoped to ["read","grep"] cannot spawn a sub-subagent with "edit". The call will fail if you try.

  - system_prompt (optional): additional system instructions appended after the role line. Use this for output format, constraints, verification rubric, or project-specific rules that shouldn't be mixed into the per-task prompt.

  - task_id (optional): pass a prior task_id to resume the same subagent session. Message history and tool outputs are preserved. Do this when a workstream has a natural follow-up — e.g. "explore auth" → (same auth subagent) "now sketch the refactor". When resuming, the allowed_tools passed in this call updates the subagent's scope going forward.

  - command (optional): the command string that triggered this task, for tracing.

Usage notes:
1. Launch multiple subagents concurrently whenever possible — one message, multiple tool_use blocks. Run independent workstreams in parallel rather than sequentially.
2. When a subagent finishes it returns a single final message. The user does not see it. You must summarize or act on it yourself. The output includes a task_id for resuming the same session later.
3. A subagent's output should generally be trusted, but verified before acting on it in high-stakes operations.

Orchestrator examples:

<example>
user: "produce a doc file for every LLM provider we support, with model table + pricing + OpenAI-compat status"
[parallel: N Task calls, one end-to-end worker per provider — each researches AND writes ITS doc]
  Task(role="provider doc owner: openai",
       allowed_tools=["websearch","webfetch","read","write","edit","task"],
       system_prompt="You own the OpenAI provider doc. Research it on the open web, produce providers/openai.md with sections: models table (name, context, pricing/1M in/out), OpenAI-compat status, notes. If the research has deep sub-topics, feel free to recurse via the task tool.",
       description="Own openai doc", prompt="...")
  Task(role="provider doc owner: anthropic", allowed_tools=[...same...], description="Own anthropic doc", prompt="...")
  Task(role="provider doc owner: google-gemini", allowed_tools=[...same...], description="Own gemini doc", prompt="...")
  // ... one end-to-end subagent per provider, spawned in parallel in a single message
[orchestrator just collects completion signals; it does not run a writing phase itself]
<commentary>
Anti-pattern that you MUST avoid: spawning 20 "researcher" subagents first, collecting their research, then spawning 20 "writer" subagents. That forces all intermediate state through the orchestrator context and serialises work across a phase barrier. One end-to-end owner per slice is faster, cleaner, and scales.
</commentary>
</example>

<example>
user: "find every place we still import the old `auth-v1` package, and rip it out"
[this task has genuinely sequential phases at the whole-repo level: you can't edit before you've located. But each located usage can be fixed end-to-end by a worker that owns read+edit+test.]
  Task(role="auth-v1 survey",
       allowed_tools=["grep","glob","read"],
       system_prompt="Return a JSON list of {file, line} for every auth-v1 import. Do not edit.",
       description="Find auth-v1 imports", prompt="...")
[orchestrator reads the survey, shards by file, spawns end-to-end fixers in parallel]
  Task(role="auth-v1 fixer: <file>",
       allowed_tools=["read","edit","bash","task"],
       system_prompt="Replace every auth-v1 import in <file> with the auth-v2 equivalent. Run `bun test` on the file's test. Stop on first failure.",
       description="Rip out auth-v1 from <file>", prompt="...")
  // ... one fixer per file, parallel
</example>

     description="Security review PR", prompt="Review changes in <file list>. ...")
